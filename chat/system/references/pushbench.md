# Push Your Agent: Measuring and Enforcing Quantitative Goal Persistence in Long-Horizon LLM Agents

- **Source:** Yuandao Cai, Yuzhang Zhu, Liyou Gao, Wensheng Tang and Shengchao Qin, "Push Your Agent: Measuring and Enforcing Quantitative Goal Persistence in Long-Horizon LLM Agents," arXiv preprint, 2026, arXiv 2605.23574 (version 1, posted 22 May 2026)
- **Type:** preprint (not peer-reviewed); four independent researchers and one Xidian University author
- **Where to find it:** https://arxiv.org/abs/2605.23574
- **Last reviewed:** 2026-11-05
- **Used by:** `chat/system/prompt.md`

## What the source covers

The paper measures whether an agent keeps working until an outside verifier confirms that a requested number of distinct valid items is complete. Its main finding is that agents lose these tasks mostly by losing track (repeating work, stopping early or running out of budget), and less by falsely claiming completion. Blocking unsupported claims of completion in the harness recovered little. Keeping a record of verified progress outside the model, and steering the model by it, recovered a lot. A prompt telling two commercial agents to track their progress changed nothing.

### Definitions

The authors call the property quantitative goal persistence. A task has an environment, an objective, a verifier that accepts or rejects each submitted unit, a target count and a step budget. A run succeeds only when the verifier has accepted at least the target number of distinct units, judged from the verifier's records and never from the agent's final message. The paper measures several failures separately: duplicate submissions, repeated attempts on finished units, premature stopping (ending or asking the user before reaching the count), false completion (claiming completion below the count) and the gap between the count the agent reports and the verified count.

### Task families and controllers

- **Repository scanning:** 36 task instances built from local snapshots of three Python projects (requests, pytest and flask), nine at each target of 10, 25, 50 and 100 artifacts, with budgets of 30 to 180 steps. The agent searches and submits artifact identifiers; the set of valid identifiers stays hidden inside the verifier.
- **Small data operations:** backlogs of small units checked by deterministic scripts (CSV field checks, file-metadata repairs, consistency answers), drawn from public datasets and the same repositories, with targets of 3, 5, 10 and 20 and six backlogs per target.

The authors deliberately kept each unit easy, so that a failure reflects lost persistence and not an unsolvable unit.

Four controllers sit between the model and the environment. The standard controller executes the model's actions. The verifier-gated controller also refuses to let the run end, or ask the user, while the verified count is below target. A state-tracking controller for scanning stores submitted identifiers and searched pages, filters duplicates, moves a repeated search to the next unseen page and blocks early stops. A backlog-tracking controller for data operations tracks each unit's status, notices loops that inspect without submitting, steers the model back to the first pending unit and prompts it to run the checker after edits. Two memory systems (Letta, formerly MemGPT, and LangGraph with memory) serve as outside baselines under the standard controller. The policies were gpt-4.1-mini, gpt-4.1 and gpt-5.4, each run once per task instance and condition, through a minimal native policy and a LangGraph implementation.

### Findings

**Repository scanning.** Under the standard controller, success ranged from 2.8 to 30.6 percent. With gpt-5.4, the native policy reached 30.6 percent and the LangGraph policy 16.7 percent, with 66 percent of its submissions duplicates. The state-tracking controller reached 69.4 to 77.8 percent for every model and policy, with no duplicate submissions at all. Paired bootstrap intervals on gpt-4.1 with LangGraph put the gain from state tracking over the standard controller at 41.7 percentage points (95 percent interval 27.8 to 58.3), against 8.3 points for verifier gating alone (interval minus 2.8 to 22.2, so possibly no gain). Many baseline runs succeeded at a target of 10 and fell toward zero by 50 or 100. An ablation found that duplicate filtering alone did no better than gating and page memory alone reached 44.4 percent, while the full controller reached 72.2 percent. Memory baselines depended on the model: with gpt-4.1-mini they completed 0 and 2 of 36 instances, and with gpt-5.4 both reached 72.2 percent, matching the controller.

**Data operations.** Standard and verifier-gated controllers completed none of the 24 backlogs, for every model and policy. The backlog-tracking controller reached 50.0 percent with gpt-4.1-mini, 29.2 percent with gpt-4.1 and 25.0 percent with gpt-5.4. Success fell as the model got stronger, which the paper does not explain. Failures in the baseline rows were mostly budget exhaustion and premature stopping; the false-completion rate was zero in every standard and gated row, so this family says little about false claims despite the paper's framing. Memory baselines reached 4.2 to 50.0 percent.

**Coding-style extension.** On small issue-style repairs in the same repositories, standard and gated controllers again completed nothing, the backlog controller reached 37.5 to 41.7 percent and the Aider coding agent reached 91.7 percent with or without the controller, which shows the units were solvable.

**Commercial agents.** Claude Code running Claude Sonnet 4.6 and Codex CLI running gpt-5.4 attempted the 18 scanning tasks with targets of 50 and 100, through a small tool interface of search, submit, status and final. One prompt told the agent to continue until the verifier's status reached the target. A checklist prompt added explicit instructions to track accepted, rejected and duplicate identifiers, searched pages, the remaining count and whether finishing was allowed. Every agent and prompt combination solved 7 of 9 tasks at 50 artifacts and 3 of 9 at 100. The checklist prompt changed duplicate counts and tool use but had no effect on success for either agent at either target.

### Strength of the evidence

The comparisons are well matched: tasks, budgets, verifiers and valid sets are identical across controllers, metrics come from verifier records and several deltas carry paired bootstrap intervals. The authors publish an anonymized artifact for reproduction and state their limits plainly.

The weaknesses matter for a prompt. The task sets are small (36 and 24 instances, one run each) and easy by design. The controllers are harness code that filters, redirects and repairs the model's actions, so their gains measure harness design, not anything a model does because of an instruction. The models are older than the ones this prompt targets (gpt-4.1, gpt-4.1-mini, gpt-5.4 and Claude Sonnet 4.6); no Claude Opus model appears. The commercial-agent evaluation has nine tasks per cell, so the null result for the checklist prompt can rule out only large effects. The inverse relation between model strength and success under the backlog controller goes unexplained, which leaves some doubt about that family's measurements.

On transfer: chat requests with a count or a full set to cover ("find 20 sources," "update every call site," "fix all failing tests") have the same structure, at smaller scale. A prompt cannot add a controller. The checklist result suggests that for a 2026 frontier agent, an instruction to track progress does not by itself fix persistence on long counted tasks, and the controller results suggest that what does help is state the harness keeps and shows the model.

## What the prompt applies

**The goal list as a stopping rule (Working loop, Before starting, first two bullets).** The prompt says the model is done when every goal is met or shown to be unmeetable. That is the paper's definition of success, with goals in place of counted units: completion is a condition checked against the work, not a feeling. The paper's evidence for enforcing the condition is weak, though. Its harness-level version, the verifier-gated controller, added at most a few points, and its prompt-level version, the checklist, added nothing. A system-prompt stopping rule is weaker than either. The paper therefore supports the definition of done more than it supports the expectation that stating it improves completion.

**Keeping the goal list in a to-do tool or file (Before starting, second bullet, last sentence).** On longer tasks the prompt tells the model to keep its goal list in a to-do tool or a file and update it as goals close. This is the prompt-level form of the paper's main positive finding, that verified progress kept in state outside the model recovers far more than any instruction. The commercial-agent result is a caution: a checklist prompt that told agents to track their state did not help, and what helped was the harness doing the tracking. The prompt's version differs from that checklist in giving the list a place to live, a tool or file, which the Claude Opus 5.5 guide also recommends; as far as the text describes, the paper's checklist prompt gave the agents no such place. Whether that difference matters is untested.

**External evidence of completion (operational goals, third bullet).** The verifier-gated controller is the harness analogue of counting a goal done only when outside evidence shows it, and its checks are part of doing the work, which matches the prompt's instruction to use the evidence the work already produces. The paper's results suggest the rule mainly keeps claims honest; it does not raise how much gets finished. Paired with the reporting bullet (Composing answers, fourth bullet), the practical value is that the user learns the true state, which corresponds to the paper's reported-count error and false-completion measures.

**Full scope and saying when the work cannot be finished (operational goals, second bullet).** Premature stopping was a large failure. In the scanning family, gpt-5.4 with LangGraph under the standard controller stopped early in 58 percent of runs. The bullet targets that failure, and the report of open goals turns an early stop into a visible one.

**Changing the angle when an approach stops producing new information (informational goals, fourth bullet).** The state-tracking controller's most useful single component moved a repeated search to an unseen page. Repeated searches and duplicate submissions are the mechanical form of the loop this bullet asks the model to break. The bullet asks the model to notice the loop itself, which the paper did not test.

## What the prompt omits

The harness half of the paper's main finding is left out: state kept and enforced by a controller, updated from the verifier's feedback, that filters duplicates and steers the model back to pending work. The prompt can only ask the model to keep its own list (see above); it cannot make the harness keep one.

The controller mechanics (duplicate filtering, page memory, steering back to pending units, prompting the checker after edits) are harness functions. The memory-system comparisons bear on choosing infrastructure, not on prompt wording. The count-specific metrics, such as reported-count error, are covered in general form by the request to report open goals.

## Conflicts with other references

**Prompting Claude Opus 5 (`anthropic-opus-5-prompting.md`; written after this section, which works from the source text).** The guide says explicit verification instructions make Claude Opus 5 over-verify and should be removed. The checks in this paper are of a different kind: queries to an outside verifier about progress, part of doing the work, not second looks at finished output. That supports the prompt's choice to define completion by outside evidence the work already produces and to rule out a separate review pass. The checklist null result also fits the guide's broader point that procedural instructions layered on a capable model's own behavior add little, although the guide's claim concerns cost and this paper measured success, on other models. `progress-mirage.md` gives the fuller analysis of whether the prompt's wording risks over-verification.

**Prompting Claude Opus 5.5 (`anthropic-opus-5-5-prompting.md`; written after this section, which works from the parts of the source I read).** For unattended runs, the guide recommends keeping the task's parts in a checklist the model updates, in a to-do tool or a file, and having the harness send a short message naming open items when a turn ends early, up to two or three times. That is close to this paper's backlog controller: state outside the model, used to steer it back to pending work. The paper gives experimental support for the guide's harness advice, though on other models. The guide's checklist and the paper's null checklist prompt are not the same intervention. The guide's list lives in a tool or file; the paper's prompt asked the agents to track state without giving them a place for it, as far as the text describes. The prompt follows the guide here, asking for the goal list in a to-do tool or file on longer tasks.

**FrontierChallenge (`frontierchallenge.md`) and When Do Agent Loops Mistake Stagnation for Progress? (`progress-mirage.md`).** All three papers find that an agent's final account of its work cannot decide completion. FrontierChallenge shows false completion claims are common on long multi-artifact work; this paper shows that, on counted tasks, losing track is the larger failure; and the progress-mirage paper shows that grounding the acceptance decision does not improve what the agent proposes. Together they suggest the prompt's evidence rule fixes what the model claims, while how much it finishes depends on state tracking, which the prompt supplies only as a list the model keeps for itself.

**Claude prompting best practices (`anthropic-prompting-best-practices.md`).** That page recommends structured state files, progress notes and git history for long tasks. This is the same idea as the paper's state finding, and the prompt takes the part a model can do itself: the goal list kept in a to-do tool or file.
