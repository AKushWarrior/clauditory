# Harness design for long-running application development

- **Source:** Prithvi Rajasekaran (Anthropic Labs team), "Harness design for long-running application development," Anthropic Engineering, published March 24, 2026. No DOI or arXiv ID.
- **Type:** company engineering post (case-study report from the model's maker, not peer reviewed)
- **Where to find it:** https://www.anthropic.com/research/harness-design-long-running-apps
- **Last reviewed:** 2026-11-05
- **Used by:** `chat/system/prompt.md`

## What the source covers

The post describes how one Anthropic engineer built a multi-agent harness that lets Claude build full-stack web applications over several hours without a person stepping in. It reports what went wrong with simpler setups, the three-agent design that fixed most of it, and a later round in which the design was cut back after a stronger model shipped. It is a practitioner's account built on a handful of runs, with costs and logs but no controlled comparison or statistics.

### Two failure modes

The author names two problems with a single agent on long tasks. The first is loss of coherence as the context window fills, plus a habit he calls context anxiety: some models start wrapping up early when they think they are near the context limit. Claude Sonnet 4.5 showed this strongly enough that summarizing earlier context in place was not enough, and the earlier harness had to clear the context and start a fresh agent from a written handoff. Claude Opus 4.5 largely lost the habit, so the later harness ran as one continuous session with automatic compaction.

The second problem is self-evaluation. Asked to grade their own output, agents praise it with confidence even when a human would call it mediocre. The post says the effect is worst on subjective work such as visual design, where no test gives a pass or fail, but that agents also show poor judgment on tasks with checkable outcomes. Splitting the worker from the judge helps. The separate judge is still an LLM and starts out lenient toward LLM output, but the author found it far easier to tune a standalone evaluator into a skeptic than to make a generator critical of its own work. Once the outside critique exists, the generator has something concrete to iterate against.

### The frontend design loop

The first experiment paired a generator with an evaluator on single-page frontend designs. The author wrote four grading criteria (design quality, originality, craft and functionality), weighted the first two more heavily because Claude already did well on the other two, and calibrated the evaluator with scored few-shot examples. The evaluator used a browser-automation tool to click through the live page before scoring it. Runs took 5 to 15 iterations and up to four hours. Scores rose and then leveled off with room to spare. The author often preferred a middle iteration to the last, and the wording of the criteria steered the style of the output in ways he hadn't expected. Even the first iteration beat an unprompted baseline, which suggests the criteria text did some of the work before any feedback arrived.

### The three-agent coding harness

For full applications the author used a planner, a generator and an evaluator.

- The planner turned a one-to-four-sentence request into a full product spec. It was told to aim high on scope and to stay at the level of product features and high-level design, leaving implementation details out. The reason given is that a wrong low-level detail in the spec would cascade into the build, so it was better to fix the deliverables and let the builder find the path.
- The generator worked in sprints, one feature at a time, and was told to check its own work at the end of each sprint before handing off.
- The evaluator used the browser tool to exercise the running app like a user, testing the interface, the API and database state. It graded each sprint against the bugs it found and against criteria for product depth, functionality, visual design and code quality. Each criterion had a hard threshold, and any miss failed the sprint.

Before each sprint, generator and evaluator negotiated a contract that defined what done meant for that chunk of work and how it would be tested, and iterated until they agreed. Agents communicated through files. One sprint's contract had 27 criteria for the level editor alone, and the evaluator's bug reports named the file, line and faulty condition.

### Results with Opus 4.5

The author gave Opus 4.5 a one-sentence request for a 2D retro game maker and ran it twice: once as a single agent and once through the full harness. The single agent took 20 minutes and cost $9. The harness took six hours and cost $200, about 22 times as much. The single-agent app looked plausible at first, but its layout wasted space, its workflow gave no guidance, and the game itself didn't respond to input because the link between entity definitions and the game runtime was broken. The planner expanded the same request into 16 features across ten sprints, well beyond what the single agent tried. The harness app was more polished and its play mode worked, though physics had rough edges and the workflow was still unclear in places.

The evaluator needed work to get there. Out of the box, Claude made a poor QA agent: in early runs it found real bugs, then talked itself into approving the work anyway, and it tested shallowly. The author tuned it over several rounds by reading its logs and correcting the prompt wherever its judgment differed from his. Even after tuning, small layout problems and bugs in deeply nested features slipped through.

### Simplifying for Opus 4.6

The author then cut the harness back, removing one component at a time after a first attempt at a radical cut failed and made it hard to tell which parts mattered. His stated principle is that each harness component encodes an assumption about what the model can't do alone, and those assumptions go stale as models improve. With Opus 4.6 he dropped the sprint structure and moved the evaluator to a single pass at the end. He kept the planner, because without it the generator under-scoped: it started building without a spec and produced a thinner app.

The evaluator's value now depended on the task. For work inside what the model handled reliably alone, it was overhead. For parts at the edge of the model's ability, it still caught real gaps. A browser-based audio workstation built this way took about 3 hours 50 minutes and $124.70, with the builder running coherently for over two hours in one stretch. The evaluator's first two rounds still found core features that were stubs or display-only, such as clips that couldn't be dragged and recording that didn't capture audio. The author concludes that the generator still tends to miss details or stub features when left alone.

### Strength of the evidence

The evidence is thin in the statistical sense. Each comparison rests on one run per configuration, judged by the person who built the harness, with no blinding, repeated trials or quantitative quality measure beyond the evaluator's own scores. The author is an Anthropic employee writing on the company's site about its own models, so the post has an interest in showing Claude in a good light, though it reports failures candidly (lenient QA, broken physics, a game level the player couldn't finish). Its most solid content is qualitative and mechanistic: the observed leniency of self-grading, the under-scoping without a planner, the stubbed features the generator left behind, and the logs showing what the evaluator caught.

Transfer to a current frontier model running this repository's prompt is partial. The post tested Sonnet 4.5, Opus 4.5 and Opus 4.6, all older than the models the prompt targets, and its own central lesson is that scaffolding goes stale as models improve. It shows that between Opus 4.5 and 4.6 the sprint structure became unnecessary and the evaluator became optional for easier work. The self-evaluation problem and the stubbing problem persisted across that jump, which makes them the findings most likely to hold for newer models. The setting also differs: multi-hour autonomous coding runs with a human-tuned evaluator, against a chat agent that serves one user turn by turn.

## What the prompt applies

**Listing goals before starting (Working loop, Before starting, first two bullets).** The prompt asks the model to list the goals a complete answer must meet, judged by what the user is trying to accomplish, and to use that list as its stopping rule. The post supports this in two ways. Without the planner, the generator under-scoped and built less than the request implied, which is the failure an up-front goal list guards against. The sprint contract defined done before any work began, which is the role the prompt gives its goal list. The post's advice to specify deliverables and leave the path open also matches the prompt's framing of goals as outcomes, not steps. The gap is that the post's planner was a separate agent with its own prompt, writing a spec another agent then built against, and its contracts were negotiated with a skeptical evaluator. The prompt asks one model to write its own goal list with no outside reviewer, which the post did not test.

**Covering the full scope (While working, operational goals, second bullet).** The rule to finish every part of the task and say when it can't be finished answers the stubbing the post documents: core features left display-only, recording reduced to a button that did nothing. The post found that an outside evaluator caught these. The prompt relies on the instruction plus the external-evidence rule below, with no second agent.

**Counting a goal done only on outside evidence (While working, operational goals, third bullet).** The prompt says the model's own sense that work is finished is not evidence, and names passing tests, a file that contains the change and a page that renders as the kind of proof it wants. This is the post's self-evaluation finding applied directly: self-grading skews positive, and the evaluator that worked was one that exercised the running app. The prompt keeps the grounding (check the artifact, not the transcript) and drops the second agent. That is a reasonable reading of the post, since what caught bugs was the browser tool's contact with the real app, but the post did not test a single agent checking its own work against tests or renders. It reports only that the generator's own end-of-sprint check did not stop bugs from reaching QA.

**Not using subagents to recheck work (While working, third bullet).** The prompt tells the model not to use subagents to recheck its own work. This runs against the post's main design, which is a separate evaluator agent. The prompt follows the Opus 5 prompting guide here (see the conflicts section). The post gives a partial basis for the choice: out of the box, an evaluator agent approved work it had found flawed, and it took several rounds of human tuning to fix. A chat model spawning an ad hoc reviewer gets none of that tuning.

**Delegating only sizeable, independent goals (While working, third and fourth bullets).** The post supports the cost side of this rule. The full harness cost about 22 times the single agent's run, and on Opus 4.6 the evaluator was overhead for work the model could do alone, worth its cost only beyond the model's solo reach. The post also supports keeping linked work with one agent: once the model improved, the builder ran a two-hour build as one continuous session, and the sprint split was removed. The post's agents, however, were not independent. They ran in a strict pipeline sharing one spec. The prompt's test of independence comes from other sources, and the post neither supports nor contradicts it.

## What the prompt omits

- **The planner, generator and evaluator roles.** The prompt has no separate planning or grading agent. A chat agent answering one user can't run a six-hour, $200 pipeline per request, and the post itself shows the evaluator turning into overhead as models improve.
- **Grading criteria and few-shot calibration.** The frontend loop's weighted criteria and scored examples were built for one domain and tuned to one person's taste. They don't generalize to a general chat prompt.
- **Sprint contracts and file-based handoffs.** The post dropped sprints itself on Opus 4.6. File handoffs serve multi-session work, which a chat agent rarely does.
- **Context resets and context anxiety.** The prompt says nothing about winding down near a context limit. The post reports that Opus 4.5 largely lost the habit, and the prompt targets later models.
- **Ambitious scoping.** The planner was told to expand scope beyond the request and to add AI features unprompted. The prompt judges goals by what the user is trying to accomplish, which is narrower on purpose, because a chat user who asks a narrow question is badly served by an expanded product.
- **Re-examining scaffolding when a model ships.** This is the post's closing lesson and applies to the prompt as a whole, but it is advice for whoever maintains the prompt, not an instruction for the model.

## Conflicts with other references

Several of the reference files named below did not yet exist in the folder when this was written. Where a file was missing, this section works from the source's local full text and says so.

- **Prompting Claude Opus 5 (`anthropic-opus-5-prompting.md`, file not yet written; read from the source).** The guide says Opus 5 verifies its own work without being told, that explicit verification steps and verification by subagent cause over-verification, and that legacy harness scaffolding adding separate verification steps should be removed. The post's core finding is that a separate evaluator caught bugs the generator missed. The two are about different models: the post's newest model is Opus 4.6, and the post itself predicts that such scaffolding goes stale. The prompt sides with the guide on subagent rechecks and keeps the post's grounding point by requiring outside evidence such as tests or a rendered page. The guide's caveat concerns added checking steps; the prompt's rule defines what counts as done, which is a different thing, though it may still add some checking cost.
- **Progress mirage (`progress-mirage.md`, file not yet written; read from the source abstract).** That paper agrees with the post that self-reports of progress are unreliable, and goes further: even a strong separate judge reading the artifact accepted many regressions, and only an evaluator with access to real-world outcomes closed the gap. This sharpens the post. The post's evaluator worked because it touched the running app, not because it was a second agent. The prompt's rule follows that sharper reading.
- **FrontierChallenge (`frontierchallenge.md`, file not yet written; read from the source abstract).** It reports that about three quarters of failed Claude Code runs still ended by claiming completion. That fits the post's self-evaluation finding with a larger sample and newer models.
- **Teams of coding agents (`coding-agent-teams.md`, file not yet written; read from the source abstract).** Cohere's study found teams beat solo agents at three to seven times the cost, with planning the most valuable thing to delegate and extra verifiers adding little. That matches the post on cost and on the value of a planning step. It differs on verification, where the post found an outside evaluator useful and the Cohere study found extra verifiers plateau. The difference likely comes from what the verifier could reach, since the post's evaluator ran the app in a browser.
- **Multi-agent versus single agent in dual-control settings and the collaboration tax (`dual-control-multi-agent.md`, `collaboration-tax.md`, files not yet written; read from the source abstracts).** Both find that multi-agent setups often lose to a single agent once the single agent is capable, and that coordination itself costs accuracy. The post's simplification for Opus 4.6 points the same way, though the post still found the multi-agent harness ahead of a single agent on its hardest tasks. The prompt's narrow delegation rule fits all three.
- **Plan compliance (`plan-compliance.md`).** That paper found that a bad or misaligned plan can hurt more than no plan, which tempers the post's support for planning. The post's planner deliberately avoided low-level steps for a related reason (errors in a detailed spec cascade), so the two agree that plans should fix outcomes and leave the method open.
