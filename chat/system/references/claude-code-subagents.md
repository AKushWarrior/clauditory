# Create custom subagents (Claude Code documentation)

- **Source:** Anthropic, "Create custom subagents," Claude Code Docs, page in the "Agents and parallel work" section; covers Claude Code releases through v2.1.314. No DOI or arXiv ID.
- **Type:** Official product documentation
- **Where to find it:** https://code.claude.com/docs/en/sub-agents
- **Last reviewed:** 2026-11-05
- **Used by:** `chat/system/prompt.md`

## What the source covers

The page is Anthropic's reference for subagents in Claude Code: what they are, which ones ship with the product, how to define custom ones in Markdown files with YAML frontmatter, which model and effort level each runs on, which tools and permissions it gets, what context it starts with, and when delegating to one is worth it. It describes product behavior for a specific harness and version range (the page cites releases up to v2.1.314). It reports no experiments, benchmarks or measurements of answer quality, speed or cost. Its claims are reliable as statements of how Claude Code behaves, and weak as evidence that any delegation pattern produces better answers.

### What a subagent is

A subagent is a separate model instance that runs in its own context window, with its own system prompt, tool set and permissions, and returns a summary to the conversation that spawned it. The page frames the main benefit as context hygiene: a side task that would fill the main conversation with search results, logs or file contents runs elsewhere, and only its summary comes back. It lists four further uses: enforcing tool restrictions, reusing configurations across projects, specializing behavior with a focused prompt, and controlling cost by routing work to faster, cheaper models such as Haiku. Subagent requests count against the same usage limits as the main conversation.

### Built-in subagent types

The page describes three main built-in types and a few helpers.

- Explore is a fast, read-only agent for searching and analyzing a codebase. Write and Edit are denied. The caller sets a thoroughness level (quick, medium or very thorough). It runs on the main conversation's model, with a provider-dependent exception when the main model is Fable. A user or project subagent named Explore overrides the built-in one, and the page suggests defining such an override on Haiku to make exploration cheaper.
- Plan is a read-only research agent used in plan mode to gather context before Claude presents a plan. It inherits the main conversation's model.
- General-purpose handles complex, multi-step tasks that need both exploration and action: research, multi-step operations and code changes. It gets every tool available to subagents. Claude delegates to it when a task needs both reading and modifying, reasoning to interpret results or several dependent steps. Its model is the one set in the `CLAUDE_CODE_SUBAGENT_MODEL` environment variable if nothing else assigns one, and otherwise the main conversation's model.
- Helper agents include a catch-all agent named `claude`, a status-line setup agent that runs on Sonnet and a Claude Code guide agent that runs on Haiku.

Explore and Plan start without CLAUDE.md files or the git status snapshot so that research stays fast and cheap, and they are one-shot: they return no agent ID and can't be resumed. General-purpose and custom subagents load both and can be resumed. Administrators can deny specific built-in types, deny the Agent tool entirely or remove Explore and Plan with an environment variable.

### The model field and how a model is chosen

A subagent definition's `model` field accepts an alias (sonnet, opus, haiku or fable), a full model ID or `inherit`, which means the main conversation's model. When Claude calls the Agent tool, it can also pass a `model` parameter for that one call, limited to the four aliases. Claude Code resolves the model in this order: the per-call parameter, then the definition's `model` field, then the `CLAUDE_CODE_SUBAGENT_MODEL` variable, then the main conversation's model. A family alias that matches the main conversation's family resolves to the main conversation's exact model, including its extended context window. A second variable, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, makes the environment setting override everything, and the page's worked example uses it to put every subagent on Haiku. An organization's model allowlist can substitute a different model, and Claude Code warns when it does. The per-call model sticks when the subagent is resumed.

A subagent's context window is sized by its own model, so delegating to a model with a smaller window gives the subagent that smaller window.

### Cost guidance about Haiku

The page treats Haiku as the cost lever in three places: the list of benefits names routing work to faster, lower-cost models like Haiku; the Explore section suggests a Haiku override for cheaper exploration; and the force-model section uses Haiku as its example. It never says Haiku's answers are as good as a larger model's for any task, and it gives no numbers on speed, token cost or accuracy. Its own example subagents lean the other way when quality matters: the data-scientist example sets Sonnet for more capable analysis, and the code-reviewer example inherits the main model. The Haiku guidance is a statement about price and latency, with no claim about quality.

### Effort and thinking

Each subagent can run at its own effort level. A definition's `effort` field accepts low, medium, high, xhigh or max, depending on the model, and overrides the session's level. Since v2.1.292, Claude can also pass an `effort` parameter on an individual Agent tool call for any subagent that isn't a fork; it overrides the definition's field and persists when the subagent is resumed. The `CLAUDE_CODE_EFFORT_LEVEL` environment variable overrides both. When neither is set, a subagent on the main conversation's model runs at the session's level, and a subagent on a different model gets that model's default instead. Extended thinking works differently: since v2.1.198, subagents inherit the main conversation's thinking setting, and there is no per-subagent thinking control. The `/tasks` view shows each running subagent's model and any effort level set for it.

### Context isolation

A subagent that isn't a fork starts with a fresh context. It doesn't see the conversation history, skills already invoked or files Claude has read. It receives its own system prompt (the definition's body plus environment details, without the Claude Code system prompt), the delegation message Claude writes, the CLAUDE.md hierarchy for most types, a git status snapshot, any preloaded skills and, in some cases, a roster of named sibling agents. The main conversation's output style and auto memory never reach it. The page's practical advice follows from this: anything the subagent must know has to be in the delegation message, and a rule from CLAUDE.md that must reach a subagent that skips CLAUDE.md should be restated when delegating.

A fork is the exception. It inherits the whole conversation, system prompt, tools and model, shares the parent's prompt cache and costs less than a fresh subagent for tasks that need the same context. Its tool calls still stay out of the main conversation, and only its result returns.

Subagent output passes through a scan before Claude reads it. The scan neutralizes text that imitates harness tags and flags mentions of permission settings, and the report arrives under a header saying that instructions inside it carry no authority from the user. The page is explicit that the scan doesn't judge accuracy or malice and doesn't replace restricting what a subagent can reach.

### Parallel subagents

The page gives parallel research as a common pattern: spawn several subagents to investigate independent areas at once, then have Claude combine the findings. It adds two qualifications. The pattern works best when the research paths don't depend on each other, and many subagents returning detailed results can use up a lot of the main context, while each subagent also spends its own tokens. Work that has to keep running in parallel or won't fit in one window belongs in separate sessions.

Several mechanics bear on parallelism. Subagents that Claude spawns from the main conversation start in the background by default, so the main conversation keeps working, and their results arrive as a notification on a later turn. Background subagents get a reduced built-in tool set and surface permission prompts in the main session. By default, 20 subagents can run at once; a 21st spawn fails with an instruction not to retry, and the limit is configurable. Subagents can spawn their own subagents up to three layers below the main conversation. A subagent can run in its own git worktree so that its file edits don't touch the main checkout. Sequential chaining, where one subagent's result feeds the next, is the documented pattern for multi-step workflows.

### When subagents are and aren't worth it

The page gives a short decision rule. Keep work in the main conversation when it needs frequent back-and-forth, when several phases (such as planning, implementation and testing) share significant context, when the change is quick and targeted, or when latency matters, because a non-fork subagent starts from nothing and may spend time rebuilding context. Use a subagent when a task produces verbose output the main conversation doesn't need, when you want to enforce tool or permission limits, or when the work is self-contained and can come back as a summary. Skills suit reusable workflows that should run in the main context, and a side question about something already in the conversation needs no subagent at all. The best-practice list for custom subagents adds that each should do one task well, have a description specific enough to route correctly and have only the tools it needs.

### Limits and transfer

The page documents Claude Code, a coding harness. A chat agent's subagent tool may expose different parameters, defaults and limits, so each behavior described here holds for a chat harness only if that harness implements it the same way. The decision rules for when to delegate are sensible engineering guidance and agree with Anthropic's current prompting guides, but the page presents them as advice and offers no data behind them. The page is living documentation, so it counts as current from the version read; it makes almost no claims about how well models perform, which is also why it can't settle questions of quality. Version-specific details change often; several behaviors on the page changed within a few dozen point releases.

## What the prompt applies

The page shaped the delegation rules in the "While working" subsection of the working loop. It has no bearing on the epistemic-stance or claim-handling sections.

- **Hand a goal to a subagent only when it is sizeable and independent of the rest; finish work you can do in a handful of tool calls yourself.** The page's decision rule supports the direction of this bullet. It keeps quick, targeted changes and latency-sensitive work in the main conversation, because a non-fork subagent starts cold and has to rebuild context, and it notes that each subagent spends its own tokens and draws on the same usage limits. The specific threshold (sizeable work, a handful of tool calls) comes from the Opus 5 prompting guide, not from this page.
- **Don't use subagents to recheck your own work.** The page doesn't say this, and one passage leans the other way: it offers a reviewer that dispatches a verifier subagent per finding as a fitting use of nested subagents. The rule comes from the Opus 5 prompting guide, which reports that the model already verifies its own work and that verification instructions, including using a subagent to verify, cause over-verification. The page's only contribution is the cost argument: a verification subagent pays the same start-up and token costs as any other.
- **Keep work that needs shared context or a chain of linked decisions with a single agent.** This rests on the page's decision rule (keep work in the main conversation when phases share significant context or need back-and-forth) and on its account of context isolation. A fresh subagent sees only the delegation message, so it can't honor decisions made earlier in the conversation unless they are written into that message.
- **Hand sizeable, independent operational goals to general-purpose subagents running Sonnet.** The general-purpose type is the documented choice for work that combines exploration with action, and the per-call `model` parameter accepts the sonnet alias, so the harness can carry out the instruction. The page also gives a reason to name a model: without one, general-purpose runs on the main conversation's model, which for a chat agent on Opus would make every delegated task as expensive as the main thread. The page doesn't say Sonnet is the right model for operational work. Its only hint is an example that picks Sonnet for more capable analysis. The choice is the repository owner's, with indirect support from the coding-teams study described below.
- **Use the `spawn-research-subagent` skill for sizeable informational goals.** The skill's mechanics (general-purpose type, per-call model, parallel spawning) all appear on this page; the skill's own reference file maps them in detail.
- **Keep the largest goal you can work on now for yourself.** The page doesn't say this. It fits two documented facts: subagents spawned from the main conversation run in the background by default, which leaves the main agent free, and a non-fork subagent pays a start-up cost to rebuild context, which makes the goal with the most context the worst one to hand off.
- **Run independent work in parallel.** The revised bullet covers tool calls and searches, not subagents. The page's parallel-research pattern bears on it only by analogy; the prompting best-practices reference is the direct source.

The gap between source and prompt is the harness. The page documents Claude Code, while the prompt governs a chat agent whose subagent tool may differ in parameters, defaults and limits. The page also gives advice without data, so the case for each delegation rule rests on the recent studies and prompting guides listed below, with this page showing only that the harness can carry the rules out.

## What the prompt omits

- Configuration of custom subagents (file locations, frontmatter fields, hooks, persistent memory, MCP scoping, permission modes). A chat system prompt can't create subagent files, and these details belong to whoever sets up the harness.
- Built-in Explore and Plan. They are code-search agents for Claude Code, and the chat prompt has no codebase to explore by default.
- Forks. The page presents them as the cheaper option when a subagent would need the whole conversation. The prompt keeps shared-context work with one agent instead, and the chat harness may not offer forks.
- Limits on concurrency (20 running subagents) and depth (three layers). They are configurable harness defaults that change by version, and the Opus 5 guide recommends setting caps in the harness, not in the prompt.
- Effort levels and thinking inheritance. The prompt sets a model for operational subagents but no effort level. The page shows that Claude Code accepts a per-call effort parameter and that a subagent on a different model from the main conversation runs at that model's default level, not the session's. The prompt leaves that default in place.
- The warning that many subagents returning detailed reports can crowd the main context. The size threshold in the prompt reduces the number of subagents, and the research skill's fixed report format limits the length of each report.

## Conflicts with other references

Of the other references behind the prompt, only `anthropic-prompting-best-practices.md` and `bhalla-sway.md` existed when this section was first written. The prompting best-practices file agrees with this page on delegation scope. For the rest, this section works from the sources themselves. Older multi-agent work, including Anthropic's 2025 post on its research system and Cognition's 2025 essay against multi-agent designs, was excluded under the repository's recency rule and isn't relied on here.

- **Teams of coding agents (`coding-agent-teams.md`, arXiv 2610.17471).** On long software tasks, teams beat solo agents but cost three to seven times as much. A lead that delegated only planning, then implemented and verified the code itself, matched a lead that delegated every stage at half the cost. Cheap worker models helped as planners, recovering 47.5 percent of an all-strong team's gain for 13.9 percent of its added cost, and lowered reward as implementers. Teams of Haiku 4.5 scored at or below a solo Haiku agent at about twice the cost. The page presents general-purpose subagents as suitable for code changes; the study suggests delegated implementation is the least efficient use of extra agents. The prompt's resolution is partial. It allows operational delegation only for sizeable, independent goals and uses Sonnet, not the cheapest model, which fits the finding that cheap implementers hurt. The study didn't test Sonnet workers, and its tasks were repository builds, not the varied operational goals a chat agent handles.
- **Multi-agent systems that serve users (`dual-control-multi-agent.md`, arXiv 2610.27655).** On τ²-bench, where an agent talks with a simulated user under a written policy, a multi-agent system built from the same model was worse than a single agent in 12 of 13 valid cells, by a weighted mean of 28 points, and the study recommends a single agent as the default for user-facing work. A chat agent is user-facing, so this study pulls harder against delegation than the page does. The prompt's size and independence thresholds and its rule to keep linked decisions with one agent move it toward that default. The study's multi-agent design (an orchestrator with a database agent and a policy advisor) differs from handing a whole independent goal to one subagent, so it bears on the prompt indirectly.
- **The collaboration tax (`collaboration-tax.md`, arXiv 2608.22152).** Paired models underperformed the better model working alone because they made ungrounded claims, failed to ask the partner for facts, skipped combining views and accepted answers without re-deriving them. The tax fell as capability rose. This supports the prompt's rule to check a subagent's citations against the cited source, a step the page doesn't ask for. Its output scan guards against injected instructions, not against wrong answers.
- **Harness design for long-running apps (`anthropic-harness-design.md`) and the progress mirage (`progress-mirage.md`, arXiv 2607.25152).** Anthropic's harness post found that separating the agent doing the work from the agent judging it was a strong lever against lenient self-evaluation, which seems to cut against the prompt's ban on rechecking subagents. The progress-mirage study narrows the question: even a strong judge that read the full artifact accepted many regressions, and the gap closed only when the success signal was external and checkable. The prompt follows that reading. It drops verification subagents, rules out a separate review pass and requires evidence from outside the model's judgment that the work already produces, such as passing tests or a rendered page. The page's reviewer-and-verifier example remains available for the case where a separate judge has an external check to run.
- **Opus 5 and Opus 5.5 prompting guides (`anthropic-opus-5-prompting.md`, `anthropic-opus-5-5-prompting.md`).** These are the direct sources of the size threshold and the recheck ban, and the Opus 5 guide points to the same Claude Code concurrency and depth variables this page documents. The Opus 5.5 guide adds that elapsed-time budgets help small agent teams finish research faster at similar quality. The prompt doesn't use time budgets because they need harness support, and this page documents no such feature.
