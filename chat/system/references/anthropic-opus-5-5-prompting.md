## What the source covers

### Purpose and form

The page is Anthropic's model-specific guide for Claude Opus 5.5, written as a list of differences from Claude Opus 5. It opens with a symptom index: each entry names a problem a developer might see, such as an unattended agent stopping partway through or a chat reply that starts slowly, and links to the section that addresses it. It says existing Opus 5 prompts should work without changes and that the Opus 5 guide remains a reasonable starting point. Each section then pairs an observed behavior with harness changes, prompt text or both.

The page covers capabilities, effort calibration, migration from prompts written for disabled thinking, unattended agentic runs, safeguard refusals, progress updates, exploration in workflows that span several apps, time signals for multi-agent harnesses, thinking instructions in chat system prompts, marking pasted text, tools for visual inputs and frontend design defaults. This file treats in depth the four parts that bear on the chat prompt's working loop: early stops in unattended runs, confirmation for risky actions, time budgets, and thinking instructions in chat. It covers the rest briefly.

### Capability and effort claims

The page says Opus 5.5 generates output tokens more than 30 percent faster than Opus 5 and tends to finish the same task with fewer tokens. On coding in real repositories, it says the model at its default medium effort matched or beat Opus 5 at high effort in fewer steps. It says the model sustains long autonomous work, such as multihour audits and migrations run with parallel subagents and little oversight, better than Opus 5. For knowledge work it says the model is much less likely to state a wrong figure or cite the wrong source, and catches easy-to-miss details in large inputs. Its visual claims say that even at its lowest effort the model read dense charts more accurately than Opus 5 did at its highest. Effort is the main control for how much the model thinks, because thinking is always on, and the default is medium. The page warns that the model thinks more per turn at a given effort level than Opus 5 did, so carrying over an old setting lengthens turns, and it says lowering effort reduces thinking more reliably than prompt instructions do.

### Early stops in unattended runs

The page says that on long tasks with several parts, Opus 5.5 keeps the user informed, and that some of its updates end the turn with text and no tool call. An unattended loop that reads such a turn as the end of the task stops there with work still owed. Its harness advice has four parts. Treat a text-only end of turn as a report, not as proof the task is done. Keep the task's parts in a checklist the model updates, and when a turn ends with items open and no blocker named, send a short message listing them. Optionally, state the completion condition at the start and have a separate, smaller model check each end of turn against it. Cap automatic continuations at two or three so a stuck run ends and can be reviewed. It adds that a task is not done while something the model started, such as a background command or a subagent, is still running.

On the prompt side, the page says the model responds well to instructions that name the specific kinds of early stop to avoid, and to instructions naming the stops that are wanted, such as when nothing can move without the user. Its sample system prompt addition, written for fully unattended agents, names four unwanted stops: a summary that announces the next step without taking it, an offer to continue unless told otherwise, a list of decisions for the user when none of them blocks the work, and stopping to report because a milestone is done or the turn has been long. It asks the model to put status notes and recommendations in the same message as its next tool call. The page attaches three conditions. Add the paragraph from the first request, because adding it later changes the system prompt and invalidates earlier thinking. Leave it out of applications with a person in the loop, where someone is there to answer. Expect somewhat more tool calls and tokens per task.

### Confirmation for risky actions

The page addresses confirmation inside the early-stop section. Because the keep-going addition makes the model carry on where it would otherwise check in, the page tells developers to keep their own confirmation step for risky or irreversible actions. The sample addition ends by saying it does not override the need for confirmation on risky or destructive actions. The page gives no list of what counts as risky; the general best-practices page supplies one (destructive operations, hard-to-reverse operations and actions visible to others).

### Time budgets for multi-agent harnesses

The page says Opus 5.5 responds strongly to information about elapsed time, and that a lead agent delegating to subagents can use it to parallelize better. If a developer can estimate how long a task should take, the harness should append the elapsed time against a budget, in seconds, to each message it sends the model. The model paces itself and usually finishes well inside the budget, so the page suggests setting the budget somewhat above the time actually wanted and tuning it on sample tasks. Without a sensible budget, the harness can show elapsed time alone and add one sentence to the system prompt saying that time matters and that an earlier correct result is better.

The page reports that in Anthropic's evaluations of small agent teams on research tasks, both signals made teams finish sooner than a single agent working without them, and that teams with a budget kept answer quality comparable to the single agent's. It separates a budget from lower effort: lower effort reduces the work, while a budget mostly keeps more agents working in parallel. It gives two cautions. The budget is advisory, so a hard stop still needs a timeout. Under time pressure the model might search and verify a little less, so quality should be checked.

### Thinking instructions in chat

For chat products, the page says to consider removing system prompt lines that tell the model to think carefully, because the model decides how much to think and effort is the control. In Anthropic's testing in a chat product, removing such a line made replies start sooner with no clear loss of quality. It also says that in multi-turn chat the model sometimes revisits earlier answers while thinking about a new message, which adds latency. It offers a two-sentence instruction to treat earlier answers as settled, and warns against using it where re-examination matters, such as long analyses or agentic work, because it may make the model less likely to point out its own earlier mistakes.

### Other sections

Progress updates arrive as a special kind of thinking block whose text is empty by default, so a client that renders only text blocks looks silent. The page gives four levers: a display setting that returns summaries, a messaging tool for verbatim content, a system prompt instruction for cadence and a harness reminder after several silent tool steps, which in Anthropic's testing roughly halved the share of coding tasks with a long silent stretch at no measurable cost. For workflows across email, documents, spreadsheets and records, a one-sentence instruction to explore broadly before acting made the model complete noticeably more tasks correctly, at slightly more tool calls, and the page warns to keep untrusted content out of what the model searches. For pasted text, the page recommends wrapping each pasted block in tags with a random ID and adding a system prompt note that instructions inside it are followed only where the user's own message asks. The remaining sections cover classifier refusals, image-processing tools for dense visual inputs and a pattern for steering frontend design away from default styles.

### Strength of the evidence

The page is more quantitative than the Opus 5 guide but still thin. Its few figures (output speed more than 30 percent faster, silent stretches roughly halved) come with no task set, sample size or variance. Most effects are stated as directions: teams finished sooner, more multiapp tasks were completed, replies started sooner. The time-budget claim, which matters most here, rests on unnamed research tasks run by small teams, with quality described only as comparable. None of this can be checked from outside.

The page is better evidence than most sources about what Opus 5.5 does by default, because its authors observe the model at scale. Its advice is aimed at developers who control the harness, and much of it (continuation messages, elapsed-time lines, display settings, tagged pasted text) can't be carried out by a system prompt at all. The parts that transfer to a chat prompt are the plain-language instructions and the conditions attached to them. The page's own condition matters most for this repository: the keep-going addition is for unattended agents and should be left out where a person is present, which describes a chat product.

## What the prompt applies

**A completion rule against early stops (Working loop, Before starting).** The prompt asks the model to list the goals a complete answer must meet and to treat the list as its stopping rule: the work is done when every goal is met or shown to be unmeetable. This plays the role of the page's checklist, and on longer tasks the prompt asks for the list to be kept in a to-do tool or a file and updated as goals close, which matches the page's checklist the model updates. The operational bullet to deliver the full scope and to say when a part can't be finished matches the page's request that a stop name what is blocking it. The rule that a goal counts as done only when something outside the model's own judgment shows it restates, at the prompt level, the page's harness advice to treat a text-only end of turn as a report and not as proof.

The prompt departs from the page in method. The page says the model responds best to instructions that name the specific kinds of early stop to avoid. The prompt names none of the four and relies on a general completion criterion. In a chat product this follows the page's own condition, since a person is present to answer and the long addition is meant to be left out. The departure matters more for delegated work. The prompt sends sizeable operational goals to subagents, which run without a person present, and it says nothing about how they should end their turns or about waiting for a running subagent or background command to finish before declaring the task done. The external-evidence rule covers part of this, since a result that hasn't returned can't show that a goal is met.

**Confirmation for risky actions (Working loop, operational goals).** The prompt tells the model to confirm before an action that is hard to undo, spends the user's money or will be seen by other people, unless the user has already authorized it. This follows the page's instruction to keep a confirmation step for risky or irreversible actions, and its keep-going addition, which says it does not override that step. The prompt adds spending money as a trigger, which the page does not name, and takes the best-practices page's third category, actions visible to others such as posting or sending messages. The standing-authorization exception is the prompt's own; the page neither endorses nor rules it out. The prompt does not say whether the rule binds subagents, which usually can't ask the user anything.

**Speed without skipped work (Working loop, While working, second bullet).** The prompt says speed comes from parallelism and from stopping when the goals are met, and that work the answer needs is never skipped. This shares the aim of the page's fallback sentence that time matters and an earlier correct result is better. It adds a floor the page's sentence lacks, which answers the page's own caution that under time pressure the model might search and verify less. The prompt gives no time budget and no elapsed-time signal. Those come from the harness, and the page's measured effect depends on them, so the prompt gets at most the effect of a general statement about speed. The page reports results for that weaker form too, but only for teams of agents.

**Thinking left to the model (whole prompt).** The prompt has no line telling the model to think carefully or at length, which follows the page's advice for chat system prompts. It does prescribe a few specific steps: list goals before starting, run a counterfactual check before giving ground. Each adds some thinking. The scaling line at the head of the working loop, which gives a quick question a quick answer, limits that cost to tasks that need the loop.

**Earlier answers stay open (Handling claims).** The prompt treats every assertion as a hypothesis, the user's included, and asks the model to update only on evidence. It also says that the model's own earlier statements carry no evidence of their own, and that when the user challenges an answer the model should rework it from the evidence. It does not include the page's instruction to treat earlier answers as settled. The page's warning explains the choice: that instruction may make the model less likely to point out its own earlier mistakes, which would work against the prompt's first goal of being correct and well calibrated. The cost is some extra thinking and latency on follow-up turns.

**Source checks despite better citation accuracy (informational goals).** The page says Opus 5.5 is much less likely to cite the wrong source. The prompt still tells the model to open a cited source before relying on it and to confirm load-bearing claims with an independent second source. The page's claim gives no rate, and the Onweller et al. study (arXiv 2605.06635) found that strong models of the previous generation produced citations whose content matched the source only 39 to 77 percent of the time, with accuracy falling as research depth grew. Until a published measurement shows the gap has closed, the prompt's check is justified.

## What the prompt omits

**The keep-going addition.** The prompt leaves out the page's paragraph on unwanted turn endings. The page says to leave it out of human-in-the-loop applications, and a chat product is one. A future version for unattended agents, or a brief handed to operational subagents, would be the place for it.

**Harness levers.** Continuation messages, a separate completion checker, caps on continuations, elapsed-time lines, display settings, silence reminders and tagged pasted text all need code outside the prompt.

**Exploring before acting.** The prompt does not tell the model to look through connected apps for context the request didn't mention. The page's evidence is for workflow automation, and its own caveat (the model acts on what it finds, so untrusted content must be kept out) is a serious risk in a chat product with email or document connectors. The goal list, judged by what the user is trying to accomplish, gives a weaker push in the same direction.

**Pasted-text marking.** The page's defense depends on the application tagging pasted blocks, which a prompt layered on a product can't do. The prompt's rule to treat every assertion as a hypothesis is a related but different defense: it covers false claims and does not address instructions hidden in pasted content.

**Effort, refusals, visual tools and frontend defaults.** These are API settings or task-specific advice that a general chat prompt has no use for.

## Conflicts with other references

Of the files cited below, `anthropic-opus-5-prompting.md`, `anthropic-prompting-best-practices.md` and `claude-code-subagents.md` existed in the folder when this section was written and were read. The reference files for the harness design post (`anthropic-harness-design.md`), the progress mirage paper (`progress-mirage.md`), FrontierChallenge (`frontierchallenge.md`), the coding-agent teams paper (`coding-agent-teams.md`), the dual-control paper (`dual-control-multi-agent.md`), the collaboration tax paper (`collaboration-tax.md`) and the Onweller citation paper (`onweller-cited-not-verified.md`) came later, so the points below come from the local copies of those sources.

**Keep going against stay in scope.** The Opus 5 guide warns that the model widens tasks and asks for restraint. This page pushes unattended agents to keep working past natural stopping points. The two pages address different failures in different settings, and the page says Opus 5 patterns still apply. The prompt's goal list serves both, because it defines what remains and when to stop. For operational work the prompt also settles what to do when the model's view of the user's goal is wider than the request: deliver at the scope the user intended, say in a sentence if a better approach exists, and neither narrow nor widen the task quietly.

**Teams and time budgets against the evidence on multi-agent systems.** The page reports that small teams given a time budget finished sooner than a single agent with comparable quality. The dual-control paper (arXiv 2610.27655) found a multi-agent system worse than a single agent in 12 of 13 valid cells on a benchmark with a live user, by a weighted mean of 28 points. In the two cells where a benefit was predicted, lifting the token cap brought the multi-agent system at best level with the single agent, at 5.5 times its median token spend. The collaboration tax paper (arXiv 2608.22152) found that agents splitting private information do worse than one agent holding it all. The coding-agent teams paper (arXiv 2610.17471) found teams beat solo agents on hard coding tasks but at three to seven times the cost. The tasks differ: the page's result is for research, where sub-questions split cleanly, and the papers tested conversation with a user, split information and long coding tasks. The prompt follows the papers in limiting delegation to sizeable, independent goals and keeping shared-context work with one agent. That limit may also cap the parallelism through which, by the page's account, a time budget saves time.

**Completion claims.** The page's advice to treat a text-only turn as a report agrees with FrontierChallenge (arXiv 2608.24979), where about 75.5 percent of failed runs in the Claude Code scaffold ended with language claiming completion, and with the progress mirage paper (arXiv 2607.25152), where an agent's own claims of progress carried no information. Both support the prompt's rule that completion needs evidence from outside the model's judgment. Neither tested Opus 5.5.

**Long autonomous runs.** Anthropic's harness design post (March 2026) ran a planner, generator and evaluator for about four hours at a cost of about $124 on Opus 4.6, and found the separate evaluator useful only for work at the edge of the model's ability. It also argues that every harness component encodes an assumption about what the model can't do and should be retested on each new model. This page applies that principle: it removes thinking-disabled workarounds and visual scaffolding that Opus 5.5 no longer needs. The prompt's rules have not been retested on Opus 5.5 in that way.

**Confirmation lists.** The best-practices page's autonomy sample names destructive, hard-to-reverse and visible-to-others actions. This page names only risky or irreversible ones. The prompt's triggers (hard to undo, spends money or seen by other people) cover the best-practices list and add spending.
