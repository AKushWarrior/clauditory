# Create custom subagents (Claude Code documentation)

- **Source:** Anthropic, "Create custom subagents," Claude Code Docs, page in the "Agents and parallel work" section; covers Claude Code releases through v2.1.314. No DOI or arXiv ID.
- **Type:** Official product documentation
- **Where to find it:** https://code.claude.com/docs/en/sub-agents
- **Last reviewed:** 2026-11-05
- **Used by:** `chat/skills/spawn-research-subagent/SKILL.md`

## What the source covers

The page is Anthropic's reference for subagents in Claude Code. It covers what they are, which ones ship with the product, and how to define custom ones in Markdown files with YAML frontmatter. It also covers which model and effort level each runs on, which tools and permissions it gets, what context it starts with, and when delegating to one is worth it. It describes product behavior for a specific harness and version range (the page cites releases up to v2.1.314). It reports no experiments, benchmarks, or measurements of answer quality, speed, or cost. Its claims are reliable as statements of how Claude Code behaves, and weak as evidence that any delegation pattern produces better answers.

### What a subagent is

A subagent is a separate model instance that runs in its own context window, with its own system prompt, tool set, and permissions, and returns a summary to the conversation that spawned it. According to the page, the main benefit is context hygiene. A side task that would fill the main conversation with search results, logs, or file contents runs elsewhere, and only its summary comes back. It lists four further uses: enforcing tool restrictions, reusing configurations across projects, specializing behavior with a focused prompt, and controlling cost by routing work to faster, cheaper models such as Haiku. Subagent requests count against the same usage limits as the main conversation.

### Built-in subagent types

The page describes three main built-in types and a few helpers.

- Explore is a fast, read-only agent for searching and analyzing a codebase. Write and Edit are denied. The caller sets a thoroughness level (quick, medium, or very thorough). It runs on the main conversation's model, with a provider-dependent exception when the main model is Fable. A user or project subagent named Explore overrides the built-in one, and the page suggests defining such an override on Haiku to make exploration cheaper.
- Plan is a read-only research agent used in plan mode to gather context before Claude presents a plan. It inherits the main conversation's model.
- General-purpose handles complex, multi-step tasks that need both exploration and action: research, multi-step operations, and code changes. It gets every tool available to subagents. Claude delegates to it when a task needs both reading and modifying, reasoning to interpret results, or several dependent steps. Its model is the one set in the `CLAUDE_CODE_SUBAGENT_MODEL` environment variable if nothing else assigns one, and otherwise the main conversation's model.
- Helper agents include a catch-all agent named `claude`, a status-line setup agent that runs on Sonnet, and a Claude Code guide agent that runs on Haiku.

Explore and Plan start without CLAUDE.md files or the git status snapshot so that research stays fast and cheap, and they are one-shot: they return no agent ID and can't be resumed. General-purpose and custom subagents load both and can be resumed. Administrators can deny specific built-in types, deny the Agent tool entirely, or remove Explore and Plan with an environment variable.

### The model field and how a model is chosen

A subagent definition's `model` field accepts an alias (sonnet, opus, haiku, or fable), a full model ID, or `inherit`, which means the main conversation's model. When Claude calls the Agent tool, it can also pass a `model` parameter for that one call, limited to the four aliases. Claude Code resolves the model in this order: the per-call parameter, then the definition's `model` field, then the `CLAUDE_CODE_SUBAGENT_MODEL` variable, then the main conversation's model. A family alias that matches the main conversation's family resolves to the main conversation's exact model, including its extended context window. A second variable, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, makes the environment setting override everything, and the page's worked example uses it to put every subagent on Haiku. An organization's model allowlist can substitute a different model, and Claude Code warns when it does. The per-call model sticks when the subagent is resumed.

A subagent's context window is sized by its own model, so delegating to a model with a smaller window gives the subagent that smaller window.

### Cost guidance about Haiku

The page treats Haiku as the cost lever in three places. The list of benefits names routing work to faster, lower-cost models like Haiku, the Explore section suggests a Haiku override for cheaper exploration, and the force-model section uses Haiku as its example. It never says Haiku's answers are as good as a larger model's for any task, and it gives no numbers on speed, token cost or accuracy. Its own example subagents lean the other way when quality matters: the data-scientist example sets Sonnet for more capable analysis, and the code-reviewer example inherits the main model. The Haiku guidance is a statement about price and latency, with no claim about quality.

### Effort and thinking

Each subagent can run at its own effort level. A definition's `effort` field accepts low, medium, high, xhigh, or max, depending on the model, and overrides the session's level. Since v2.1.292, Claude can also pass an `effort` parameter on an individual Agent tool call for any subagent that isn't a fork; it overrides the definition's field and persists when the subagent is resumed. The `CLAUDE_CODE_EFFORT_LEVEL` environment variable overrides both. When neither is set, a subagent on the main conversation's model runs at the session's level, and a subagent on a different model gets that model's default instead. Extended thinking works differently: since v2.1.198, subagents inherit the main conversation's thinking setting, and there is no per-subagent thinking control. The `/tasks` view shows each running subagent's model and any effort level set for it.

### Context isolation

A subagent that isn't a fork starts with a fresh context. It doesn't see the conversation history, skills already invoked, or files Claude has read. It receives its own system prompt (the definition's body plus environment details, without the Claude Code system prompt) and the delegation message Claude writes. It also receives the CLAUDE.md hierarchy for most types, a git status snapshot, any preloaded skills, and, in some cases, a roster of named sibling agents. The main conversation's output style and auto memory never reach it. The page's practical advice follows from this: anything the subagent must know has to be in the delegation message, and a rule from CLAUDE.md that must reach a subagent that skips CLAUDE.md should be restated when delegating.

A fork is the exception. It inherits the whole conversation, system prompt, tools, and model, shares the parent's prompt cache, and costs less than a fresh subagent for tasks that need the same context. Its tool calls still stay out of the main conversation, and only its result returns.

Subagent output passes through a scan before Claude reads it. The scan neutralizes text that imitates harness tags and flags mentions of permission settings, and the report arrives under a header saying that instructions inside it carry no authority from the user. The page is explicit that the scan doesn't judge accuracy or malice and doesn't replace restricting what a subagent can reach.

### Parallel subagents

The page gives parallel research as a common pattern: spawn several subagents to investigate independent areas at once, then have Claude combine the findings. It adds two qualifications. The pattern works best when the research paths don't depend on each other, and many subagents returning detailed results can use up much of the main context, while each subagent also spends its own tokens. Work that has to keep running in parallel or won't fit in one window belongs in separate sessions.

Several mechanics bear on parallelism. Subagents that Claude spawns from the main conversation start in the background by default, so the main conversation keeps working, and their results arrive as a notification on a later turn. Background subagents get a reduced built-in tool set and surface permission prompts in the main session. By default, 20 subagents can run at once; a 21st spawn fails with an instruction not to retry, and the limit is configurable. Subagents can spawn their own subagents up to three layers below the main conversation. A subagent can run in its own git worktree so that its file edits don't touch the main checkout. Sequential chaining, where one subagent's result feeds the next, is the documented pattern for multi-step workflows.

### When subagents are and aren't worth it

The page gives a short decision rule. Keep work in the main conversation when it needs frequent back-and-forth, when several phases (such as planning, implementation, and testing) share much context, when the change is quick and targeted, or when latency matters. A non-fork subagent starts from nothing and may spend time rebuilding context. Use a subagent when a task produces verbose output the main conversation doesn't need, when you want to enforce tool or permission limits, or when the work is self-contained and can come back as a summary. Skills suit reusable workflows that should run in the main context, and a side question about something already in the conversation needs no subagent at all. The best-practice list for custom subagents adds that each should do one task well, have a description specific enough to route correctly, and have only the tools it needs.

### Limits and transfer

The page documents Claude Code, a coding harness. A chat agent's subagent tool may expose different parameters, defaults, and limits, so each behavior described here holds for a chat harness only if that harness implements it the same way. The decision rules for when to delegate are sensible engineering guidance and agree with Anthropic's current prompting guides, but the page presents them as advice and offers no data behind them. The page is living documentation, so it counts as current from the version read; it makes almost no claims about how well models perform, which is also why it can't settle questions of quality. Version-specific details change often; several behaviors on the page changed within a few dozen point releases.

## What the skill applies

- **Description and "When to use": fan out only when the task splits into independent sub-questions or needs heavy reading.** This rule follows the page's parallel-research pattern, which works best when paths don't depend on each other, and its decision rule that subagents suit self-contained work whose bulky output the main conversation doesn't need. Heavy reading across many sources is the page's high-volume case: the reading stays in the subagent's context and only the summary returns.
- **Skip single facts.** The page backs the direction of this rule. A non-fork subagent starts cold and may take time to rebuild context, and each subagent spends its own tokens. The figures in the skill (about 53 seconds and 96,000 tokens for a fact that one search and two fetches had answered) come from the owner's own test, not from the page. They are one trial, useful as an illustration and not as a measured average.
- **How, step 1: one subagent per sub-question, all in the same message, with subagent_type general-purpose and model haiku.** Spawning in one message matches the parallel pattern and the background-by-default behavior. General-purpose is the right type because research needs web search and fetch tools; Explore and Plan are read-only code-search agents tied to a codebase. Passing haiku per call is supported: the Agent tool accepts the alias, and the per-call parameter outranks the definition and environment defaults. The page backs Haiku on cost and speed only. It makes no claim that Haiku researches as well as a larger model, so the choice trades some quality for speed and cost and relies on step 3 to catch errors.
- **How, step 1: Haiku is the speed and cost lever; leave reasoning effort at its default unless the person asks.** The revised wording matches the page. Claude Code accepts a per-call `effort` parameter on non-fork subagents (v2.1.292 or later), so effort is settable, and the skill chooses not to change it. The page adds a detail the skill relies on without stating it. A subagent on a different model from the main conversation doesn't inherit the session's effort level and runs at its own model's default. A Haiku subagent under an Opus lead, for example, runs at Haiku's default, not the lead's setting. Extended thinking is the one control with no per-subagent setting; subagents inherit it from the main conversation.
- **Template: a self-contained brief with the question, source ranking, stopping rule, and report format.** Context isolation is the reason a template is needed at all. A fresh subagent sees none of the conversation, so everything it needs, including the standard for sources and the shape of its answer, has to be in the delegation message. The fixed four-line report format also addresses the page's warning that many detailed reports can crowd the main context.
- **How, step 3: check every load-bearing claim against the primary source before relaying it.** The page gives only indirect support. It marks subagent reports as the subagent's words, without the user's authority, and says its output scan doesn't judge accuracy. It says nothing about how often reports are wrong; the attribution study below supplies that evidence.

## What the skill omits

- Custom subagent definitions. A dedicated research subagent file could fix the model, tools, effort, and template in one place. A skill can't rely on the user having installed one, and passing the template in the delegation message works in any harness with a general-purpose type.
- Forks. A fork would carry the full conversation and share the prompt cache, but research sub-questions are meant to be independent, and the skill wants each subagent to work from the brief alone.
- The concurrency limit (20 by default) and nesting depth (three layers). Research fan-outs rarely approach either, and the numbers are configurable defaults.
- Background execution details. The page says background results arrive on a later turn and that the main agent must wait for them before reporting. The skill's step 3 implies waiting but doesn't say so, which matters in a harness where the main agent could otherwise answer before the reports land.

## Conflicts with other references

The other reference files in this folder were written alongside this one, so this section works from the sources themselves.

- **Cited but not verified (`onweller-cited-not-verified.md`, arXiv 2605.06635).** Across 14 models writing cited research reports, links nearly always worked and were usually relevant, but the cited source supported the claim only 39 to 77 percent of the time among the stronger models. Claude Haiku 4.5 scored 68.9 percent on that check, above Sonnet 4.6 at 58.7 percent and below Opus 4.5 at 76.8 percent. In an ablation on two models, accuracy fell by about 42 percentage points on average as the tool-call cap rose from 2 to 150. The study supports the skill's step 3 far more directly than the page does, and it gives some comfort on the Haiku choice: on this measure Haiku wasn't the weak link. It also qualifies the skill's premise that heavy reading is a reason to fan out. More reading per agent didn't produce more accurate citations, so the benefit of delegation is keeping the reading out of the lead's context, not making it more reliable.
- **Trust, but don't verify (`pradhan-trust-dont-verify.md`, arXiv 2606.05403).** Models weighed sources by whether they sounded methodologically rigorous, not by whether their numbers were valid, and a prompt checklist naming the exact checks produced blanket skepticism instead of better discrimination. The template tells subagents to judge sources by provenance and method, to treat polish, popularity, and authority cues as weak signals, and to weigh each source on its own record instead of distrusting all of them equally. The last clause is aimed at the blanket skepticism the study found. The study gives no evidence that a sentence like it makes a model selective, though, and a scrutiny instruction of this kind is the sort of prompt it found ineffective. The page has nothing to say on source evaluation. The skill's backstop is again step 3: the lead opens the cited source itself instead of trusting the subagent's judgment of it.
- **Teams of coding agents (`coding-agent-teams.md`, arXiv 2610.17471).** Cheap worker models paid off when they gathered information for a strong lead and hurt when they produced work the lead had to integrate. A strong lead with cheap planners recovered 47.5 percent of an all-strong team's gain for 13.9 percent of its added cost. Research subagents that report findings to a stronger lead fit the profitable pattern, which supports the Haiku choice. The support is indirect. The study's planning workers explored a program's behavior for a software task, not the web. Teams made entirely of Haiku 4.5 scored at or below a solo Haiku agent at about twice the cost. The skill avoids that case because the lead stays on the main conversation's model.
- **Wineburg and McGrew, lateral reading (`wineburg-mcgrew-lateral-reading.md`).** The study found that professional fact-checkers judged unfamiliar websites better than historians and students by leaving a site quickly and checking what other sources said about it. The template's instructions to judge provenance and confirm load-bearing claims with an independent second source come from that work. The page has nothing on source evaluation, and its cost guidance points to the smallest model; the tension is that lateral reading takes judgment. The skill accepts that risk and makes the lead's own check the safeguard. The study measures people, not AI, so the recency rule doesn't apply. Its full text wasn't available locally, so this comparison rests on the study's widely reported findings, not a fresh reading of the paper.
