# clauditory-lint

clauditory-lint checks prose against every rule in the writing-style and technical-writing skills that a program can test, and it fixes the problems that have one mechanical fix. It is one Go program with the Vale prose linter compiled in, so you don't need to install anything else.

## What it checks

- **House rules.** The writing-style skill's own choices come first. The linter flags every em dash and en dash, and every hyphen or run of hyphens used as a dash, and it asks for the serial comma. It also checks the patterns in the skill's revision pass, such as correction framing, trailing participles, stock openers, announcements, hedge stacks, and the vocabulary machine-written text leans on. Its rhythm check flags a paragraph whose sentences all run about the same length.
- **Machine-writing tells.** The vale-ai-tells style, which catches figurative verbs, false balance, strawman contrasts, announcement headings, closing pleasantries, and many other habits of model prose. A few of its rules that contradict the skill are off.
- **Style-guide rules.** The linter checks the word forms and mechanical rules of nine guides: The New York Times Manual of Style and Usage, the AP Stylebook, The Chicago Manual of Style, New Hart's Rules and the New Oxford Dictionary for Writers and Editors, the IBM Style Guide, the Apple Style Guide, the Google developer documentation style guide, the Microsoft Writing Style Guide, and the Red Hat style guides. Red Hat's official Vale style and the community Microsoft style are included unchanged; the rest were extracted from the guides themselves.

Where two guides disagree, the linter reports only one of them, and it never reports a rule that contradicts the skills. It skips code, URLs, and words inside double quotes, so text that quotes a banned phrase doesn't trip the rule it describes. Run `clauditory-lint rules` to see every rule, its fix setting, and, for a rule that is off, why.

## Run it

In an agent session with the Clauditory plugin or the writing-style skill installed, the skill's `scripts/lint` launcher runs the build for the current machine:

```
scripts/lint draft.md                          # report problems
scripts/lint --fix draft.md                    # apply the safe fixes in place, then report the rest
scripts/lint --fix=all draft.md                # also apply fixes that need a look
scripts/lint < reply.md                        # check standard input as Markdown
git log -1 --format=%B | scripts/lint --commit # check a commit message
scripts/lint --format=json notes.md            # machine-readable output
```

From a clone of this repository, `bin/clauditory lint` takes the same flags and builds the linter for your machine first.

The `--min` flag sets the lowest severity to report, and `--fail` sets the lowest severity that makes the exit status 1 (the default is error). Status 2 means the linter itself failed.

A safe fix has one correct result, such as `utilize` to `use` or `5 November 2026` to `November 5, 2026`. A fix that needs a look, such as spelling out a small number, is right in most sentences but wrong in some, so it runs only with `--fix=all`. Rules that need judgment report the problem and leave the rewrite to the writer.

Code spans, code blocks, URLs, and front matter aren't checked. To turn the linter off for part of a Markdown file, wrap it in `<!-- vale off -->` and `<!-- vale on -->`.

## Claude Code hook

The Clauditory plugin runs the linter after Claude writes or edits a Markdown, text, reStructuredText, or AsciiDoc file, and passes any warnings and errors back to Claude, which can then fix them. Set `CLAUDITORY_LINT_HOOK=off` to turn the hook off, or put the text `clauditory-lint: off` anywhere in a file to skip that file.

## How it's packaged

The skill's `scripts/bin` folder holds one build per platform (Linux, macOS, and Windows, on x86-64 and ARM where they apply), each about 6 MB and compressed with xz. On first use the launcher unpacks the build for the current machine into a cache folder, with `xz` or, where `xz` is missing, Python's `lzma` module, and reuses it after that. The builds are generated by `bin/clauditory build` and aren't kept in the source tree.

## Layout

```
cmd/clauditory-lint/   the command
registry.go            loads rules.yml and rules.gen.yml and settles conflicts
alerts.go              runs the embedded Vale engine, filters alerts, and applies fixes
terms.go               matches the extracted word lists, which are too large for Vale
internal/vale/         Vale 3.26.0, vendored with its tree-sitter code parsers removed
rules.yml              each hand-written and vendored rule's fix setting and status
rules.gen.yml          the same for the extracted rules (generated)
terms.gen.json         the extracted word lists and patterns (generated)
styles/                Vale styles, one folder per source
sources/               the rules extracted from each guide, and prune.tsv
tools/                 genrules.py, prune.py, expand.py, and dist.sh
hooks/hooks.json       the Claude Code hook, copied into the plugin by bin/clauditory build
references/            the sources behind the linter
testdata/              fixtures for go test
```

To change the extracted rules, edit the files in `sources/`, then run `tools/genrules.py` and `tools/prune.py` (see the comments at the top of each) and `go test ./...`.
